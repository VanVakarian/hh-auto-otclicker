# HH Auto Otclicker — implementation plan

## Цель

Chrome-расширение с боковой панелью: автономно откликается на вакансии на hh.ru (до ~200/день), само проходит анкеты через LLM, само листает страницы поиска, само возвращается туда, где остановилось. Три экрана: Запуск, Аналитика, Настройки.

## Разведка целевых страниц (debug-htmls)

По сохранённым снапшотам разобраны три сценария отклика:

- **Мгновенный отклик** — клик по кнопке отклика на карточке в списке вакансий, без перехода на другую страницу и без модалки.
- **Отклик через попап (без перехода)** — hh.ru показывает модальное окно «Отклик на вакансию» прямо поверх списка, когда единственное дополнительное требование — сопроводительное письмо (без вопросов анкеты). В модалке: заголовок вакансии, резюме (по умолчанию), textarea письма (`data-qa="vacancy-response-popup-form-letter-input"`), кнопка отправки (`data-qa="vacancy-response-submit-popup"`, задизейблена, если письмо обязательно и не заполнено) и крестик закрытия (`data-qa="response-popup-close"`). Обрабатывается целиком внутри `vacancy-list.js`, без перехода на другую страницу.
- **Отклик с анкетой** — клик переводит на `/applicant/vacancy_response?vacancyId=...`. Там: текст анкеты, один или несколько вопросов двух типов — свободный текст (textarea) и выбор варианта (radio-группа, среди вариантов почти всегда есть «Свой вариант», раскрывающий скрытую textarea). Ниже — переключатель сопроводительного письма (по клику раскрывает textarea) и кнопка отправки анкеты.
- Список вакансий: карточка вакансии, кнопка отклика с `href`, содержащим `vacancyId`; пагинация — обычные ссылки-страницы + «следующая».

Полностраничная анкета матчится по URL (`/applicant/vacancy_response*`) — под неё отдельный content script. Список и попап живут на одной странице (`/search/vacancy*`) и обрабатываются одним и тем же `vacancy-list.js`: после клика по отклику скрипт поллингом определяет, что произошло — переход на анкету, появление модалки или мгновенный успех — и действует по ситуации.

## Ключевые архитектурные решения

- **Источник списка вакансий — сам hh.ru.** Расширение не строит поисковые фильтры само: пользователь настраивает поиск на hh.ru как обычно и жмёт «Старт» в панели, пока эта вкладка активна. Просто и надёжно, не дублирует чужой UI.
- **Восстановление позиции — через прямой URL, а не back().** После анкеты/отклика фон помнит URL страницы списка (с номером `page`) и возвращает вкладку туда через `tabs.update`, а не через историю браузера — навигация браузерной историей на SPA хрупкая, прямой URL детерминирован.
- **Дедупликация — по `vacancyId`, а не по чёрному списку вакансий.** Источник истины «откликались/нет» — сама кнопка на странице hh.ru (есть кнопка «Откликнуться» → не откликались). Внутри одного прогона держим set обработанных `vacancyId`, чтобы не задвоить при перерендере страницы.
- **Один унифицированный контракт ответов LLM.** Для вопросов с вариантами (radio и checkbox — множественный выбор просим через «; ») передаём варианты текстом прямо в промпте; просим LLM вернуть точный текст варианта(ов) или свободный текст, если ни один не подходит. LLM никогда не «видит» DOM и не кликает сама — только возвращает текст; весь маппинг текста обратно на конкретные radio/checkbox делает content script. Три уровня сопоставления по надёжности: 1) точное/подстрочное совпадение с текстом варианта — кликаем; 2) если не совпало и есть поле «Свой вариант» — открываем его и вписываем ответ LLM как есть; 3) если совпадения нет и своего поля тоже нет — берём вариант с максимальным пересечением слов (иначе вопрос так и остался бы без ответа). LLM-модуль остаётся близким к Quiz Solver (`answers: string[]`), без усложнения схемы.
- **Список моделей LLM — настраиваемый, с дефолтом в коде.** В Настройках — необязательное поле «Модели LLM» (textarea, по одной на строку); если пусто — используется встроенный список по умолчанию. `lib/llm.js` пробует модели по порядку, пока одна не даст валидный ответ — логика фолбэка не изменилась, изменился только источник списка.
- **Сопроводительное письмо — одно заранее заданное, без генерации под вакансию.** Дёшево и предсказуемо, как и просил пользователь.
- **LLM — отключаемый модуль, а не обязательная зависимость.** Настройка «Заполнять анкеты через LLM» (выключена автоматически, если не задан API-ключ). Если на анкету наткнулись при выключенном LLM — либо все модели не дали валидный ответ — content script ничего не заполняет и не отправляет, просто сигналит фону «анкета не пройдена». Тот же путь для обеих причин (LLM выключен / LLM не справился) — не нужно два отдельных механизма.
- **Постоянный «анкетный» чёрный список вакансий.** При «анкета не пройдена» — а теперь и при «попап с обязательным письмом, текста которого нет» или «попап с вопросами внутри (не поддерживаем)» — content script добавляет `vacancyId` (+ название, компания, причина, дата) в отдельный персистентный список в storage, закрывает модалку крестиком (не оставляет её висеть) и продолжает прогон со следующей вакансии. Список не привязан к дню/прогону, живёт до ручного сброса. `vacancy-list.js` перед кликом по отклику проверяет карточку и на этот список тоже (наравне с ЧС компаний) — при повторной встрече с той же вакансией в будущих прогонах клика вообще не будет. Кнопка «Сбросить» в Настройках очищает список полностью.
- **Детект «клик сработал» — по подписи кнопки, а не только по её наличию.** hh.ru иногда оставляет тот же элемент отклика в DOM после успешного мгновенного отклика, просто меняя подпись (не убирает кнопку) — проверка «кнопки больше нет» этого не ловила и давала ложные «клик не сработал». Теперь дополнительно проверяем, что текст кнопки всё ещё содержит «Откликнуться»; таймаут ожидания исхода клика увеличен до 6 сек, чтобы не спешить с выводом на медленном рендере попапа.
- **Скролл к карточке перед кликом.** Перед откликом `vacancy-list.js` скроллит карточку вакансии в центр экрана (`scrollIntoView({block:'center'})`) и ждёт, пока анимация осядет — и нагляднее при наблюдении за прогоном, и больше похоже на поведение человека.
- **Инъекция content script — программная (`webNavigation` + `scripting`), а не статическая через `manifest.content_scripts`.** hh.ru — SPA: переход по «Откликнуться» может быть pushState-навигацией без перезагрузки документа, на которую статические content scripts просто не переинжектируются. Фон слушает `onCompleted` (обычная навигация) и `onHistoryStateUpdated` (SPA-переход) и сам вставляет нужный скрипт — работает независимо от того, как именно hh.ru рендерит переход.
- **Оркестрация — в background service worker, а не в content script.** MV3-воркер переживает навигации внутри вкладки (в отличие от content script, который уничтожается при переходе). Всё состояние прогона — в `chrome.storage.local`, воркер — просто читает/пишет его и реагирует на события вкладки и сообщения от content script. Это даёт устойчивость к перезапуску воркера.
- **Пагинация — клик по нативным ссылкам пагинации hh.ru**, а не попытка сконструировать URL самостоятельно (у hh.ru сложные query-параметры фильтров, которые проще не трогать).
- **Дневной лимит — по календарным суткам (локальное время), персистентно.** Считает успешные отклики за сегодня независимо от того, сколько раз жали «Старт»/«Стоп» за день.
- **Случайные паузы между действиями.** Защита от анти-бот эвристик hh.ru при объёме 200/день — обязательная часть цикла, не опция «на будущее».

## Компоненты

- **`background.js`** — оркестратор/машина состояний прогона: держит run-state в storage, слушает `tabs.onUpdated`/сообщения от content scripts, решает следующий шаг (кликнуть отклик → дождаться результата → если анкета — дождаться её обработки → вернуться на список → следующая карточка/страница), считает дневной лимит и статистику, пишет лог событий для аналитики и diagnostic-лог при ошибках, управляет бейджем на иконке при статусе «Ошибка».
- **`content-scripts/vacancy-list.js`** — матчится на `/search/vacancy*`. Сканирует карточки, фильтрует по чёрному списку компаний, кликает отклик по следующей необработанной вакансии, сообщает фону результат (мгновенный успех / переход на анкету), при исчерпании страницы — кликает «следующая страница».
- **`content-scripts/vacancy-questionnaire.js`** — матчится на `/applicant/vacancy_response*`. Извлекает вопросы обоих типов, запрашивает у фона ответы через LLM-модуль, заполняет radio/textarea, при включённой настройке — раскрывает и заполняет сопроводительное письмо, жмёт отправку, сообщает фону готовность.
- **`llm/answer-generator.js`** — перенос `llm-integration.js` из Quiz Solver почти без изменений (OpenRouter, фолбэк по моделям, устойчивый парсинг JSON).
- **`sidepanel/`** — три вкладки: Запуск, Аналитика, Настройки. Читает run-state и лог из storage (и/или сообщений от фона), не привязана к активной вкладке браузера — отражает состояние фонового прогона, а не текущую страницу (в отличие от Quiz Solver, где панель реагировала на активную вкладку).

## Хранилище (chrome.storage.local)

- **Настройки** — API-ключ, легенда, стиль-промпт (перенос из Quiz Solver один в один) + переключатель «Заполнять анкеты через LLM» + дневной лимит откликов + диапазон паузы между действиями + текст сопроводительного письма и переключатель «прикладывать» + список компаний чёрного списка (textarea, одна компания на строку).
- **Run-state** — статус (idle/running/stopped/error), URL/страница списка для возврата, набор обработанных за прогон `vacancyId`, счётчики (отклики/пропуски/ошибки), время старта, текущая обрабатываемая вакансия — для живого отображения на экране «Запуск».
- **Анкетный чёрный список вакансий** — отдельный персистентный массив: `vacancyId`, название, компания, причина пропуска (LLM выключен / LLM не справился), дата. Не связан с run-state и не чистится по дням — только вручную, кнопкой «Сбросить» в Настройках.
- **Лог/статистика** — по каждому отклику: время, вакансия, компания, тип (мгновенный/анкета), результат (успех/ошибка/пропуск по ЧС компаний/пропуск по анкетному ЧС). Хранится с ротацией/агрегацией по дням, чтобы не расти бесконечно — для экрана «Аналитика».
- **Diagnostic-лог** — отдельный кольцевой буфер последних ~200 warning/error-событий (время, модуль, сообщение, контекст). Не для аналитики пользователю, а для быстрой диагностики поломок — источник для кнопки «Скопировать диагностику».

## Экраны

- **Запуск** — кнопки Старт/Стоп, текущий статус (включая «Ошибка» с текстом причины), счётчик «откликов сегодня / дневной лимит», текущая обрабатываемая вакансия, мини-лента последних событий (warning/error выделены), кнопка «Скопировать диагностику».
- **Аналитика** — столбчатый график откликов за последние 7 дней (простой, без сторонних библиотек), итоги (всего/сегодня/за неделю), разбивка мгновенные/анкетные/пропущенные по ЧС/ошибки, таблица последних откликов.
- **Настройки** — все поля из Quiz Solver (API-ключ, легенда, промпт стиля) + переключатель «Заполнять анкеты через LLM» + дневной лимит + диапазон пауз + сопроводительное письмо (текст + переключатель) + чёрный список компаний (textarea, по одной на строку) + анкетный чёрный список вакансий (счётчик записей + кнопка «Сбросить»).

## Визуальный стиль

Принцип: симпатично и по-фирменному, не голый минимализм. Основной цвет — красный, в тематике HH (`#d6001c`, тёмный `#a80016` для hover/акцентов).

- Мини-шапка панели: красный бейдж-логотип «HH» + название — сразу считывается как фирменный инструмент, а не безликая форма.
- Красный — цвет кнопок, активной вкладки, счётчиков, графика (кнопки и активная вкладка — с лёгким градиентом красный→тёмно-красный и мягкой тенью в тон, не плоская заливка).
- Индикатор «идёт прогон» — зелёная пульсирующая точка (сохраняем интуитивно понятный «зелёный = работает», чтобы не спорить с красным брендингом), ошибка — отдельный красно-оранжевый тон, чтобы не сливаться с фирменными кнопками.
- Чёткая типографическая иерархия: заголовок экрана, подписи полей, второстепенный текст — разными весом/размером, не только цветом.
- Карточки крупнее скруглены (16px) и с мягкой многослойной тенью — мягче и «дороже» на вид, чем плоские блоки.
- Щедрые отступы и группировка карточками, не плотная простыня полей.
- Живые, но ненавязчивые микро-состояния: пульсирующий статус, плавные transition на hover/active/disabled, лёгкий подъём/свечение у кнопок при наведении.
- Пустые состояния оформлены (например: «пока нет откликов» на Аналитике), а не пустая белая зона.
- Единый компонентный язык кнопок/полей/карточек между всеми тремя экранами — одни и те же классы, не изобретать стиль заново под каждый экран.

## Риски и меры

- Капча/бан/неожиданная страница hh.ru → воркер должен распознать «страница не похожа на ожидаемую» и остановить прогон с понятной ошибкой в UI, а не зациклиться.
- LLM выключен, нет ключа, либо все модели не ответили валидным JSON → анкета не заполняется, вакансия уходит в анкетный ЧС, прогон продолжается со следующей вакансии (не ошибка прогона).
- Слишком частые действия → рандомизированные паузы + дневной лимит как встроенные меры, а не постфактум-настройка.

## Диагностика и обработка ошибок

Цель — по логам и статусу быстро понять, что и почему сломалось, без ручного воспроизведения.

- **Принцип «неожиданное — это сигнал, а не тишина».** Каждый content script перед действием проверяет, что ожидаемые элементы страницы на месте. Не нашёл — не гадает и не крутится в цикле, а сразу репортит фону структурированную ошибку с контекстом (URL, что искали, что нашли вместо этого), и прогон останавливается.
- **Единая консольная конвенция логов.** Короткие однострочные записи с фиксированным префиксом-эмодзи на модуль (список вакансий / анкета / фон / LLM) — удобно фильтровать в DevTools по модулю. Конкретные значения (id, счётчики, статусы), не дампы целых DOM-узлов/объектов.
- **Три разные консоли — поэтому критичное дублируется в storage.** Content script живёт в консоли вкладки hh.ru, background — в консоли service worker расширения, side panel — в своей. Ловить нужный момент в DevTools не всегда реально, поэтому warning/error всегда параллельно пишутся в persistent-лог (см. ниже), а не только в console.
- **Persistent диагностический лог.** Отдельно от лога откликов (аналитика) — кольцевой буфер последних ~200 warning/error-событий по всем модулям: время, модуль, сообщение, контекст (URL/vacancyId/что происходило). Переживает перезапуск service worker и закрытие DevTools.
- **Сигнализация в UI.** На экране Запуск статус «Ошибка» с текстом последней проблемы; бейдж на иконке расширения (заметно даже при закрытой панели); в живой ленте warning/error визуально отличаются от обычных событий.
- **Кнопка «Скопировать диагностику».** Один клик — копирует в буфер обмена последние diagnostic-события + снимок run-state + версию расширения (без API-ключа), чтобы делиться при обращении за доработкой без пересказа словами.

## Не входит в первую версию (по решению пользователя)

- Общий чёрный список всех откликнутых вакансий (не нужен — источник истины — сама кнопка hh.ru; персистентный список ведём только для анкет, которые не смогли пройти).
- Индивидуальная генерация сопроводительного письма под каждую вакансию.
- Выбор резюме для отклика (используется резюме, предзаданное по умолчанию на странице hh.ru).

## Находки после ревью (codex-review, 12.08.2026)

1. Нет разрешения на OpenRouter в манифесте
   - **Важность:** срочно по классификации, но, вероятно, ложное срабатывание — под вопросом
   - **Как сейчас работает:** Манифест разрешает расширению обращаться только к `hh.ru`. Запросы к OpenRouter (для генерации ответов на анкету) идут из фонового скрипта.
   - **Что не так:** Codex считает, что без явного разрешения на `openrouter.ai` в `host_permissions` браузер заблокирует эти запросы — и тогда генерация ответов LLM не будет работать вообще, анкеты будут всегда падать в «LLM не справился». Оговорка: на практике страницы расширений (в т.ч. фоновый service worker) обычно могут делать `fetch` на любой домен без `host_permissions` — это ограничение относится в первую очередь к content script и к обходу CORS чужой страницы, а не к запросам из фона. Ровно такой же паттерн уже использовался в родственном расширении Quiz Solver и, судя по всему, работал.
   - **Как поправить:** в любом случае добавить `https://openrouter.ai/*` в `host_permissions` — стоит копейки, гарантированно снимает вопрос независимо от того, кто прав.
   - **Как будет работать после правки:** запросы к OpenRouter точно не будут упираться в разрешения браузера, при любом устройстве MV3.

2. Отправка анкеты считается успешной без подтверждения
   - **Важность:** срочно
   - **Как сейчас работает:** после клика на кнопку отправки анкеты скрипт просто ждёт 1 секунду и сразу пишет в лог «успех», прибавляет отклик к дневному счётчику.
   - **Что не так:** если hh.ru не принял анкету (не заполнено обязательное поле, ошибка валидации, сетевой сбой) — вакансия всё равно уйдёт в статистику как успешно отправленная, хотя по факту отклика не было.
   - **Как поправить:** после клика дождаться реального подтверждения (страница перестала быть анкетой, кнопка сменила состояние на «отправлено», и т.п.), а не фиксированной паузы; если подтверждения не дождались — считать ошибкой/пропуском, не расходовать дневной лимит.
   - **Как будет работать после правки:** в статистике и в дневном лимите будут только реально отправленные анкеты.

3. Успех попапа с письмом тоже не подтверждается
   - **Важность:** срочно
   - **Как сейчас работает:** для попапа «Отклик на вакансию» код ждёт исчезновения попапа (`waitFor`) — но результат этого ожидания нигде не проверяется, дальше код безусловно идёт по ветке успеха.
   - **Что не так:** если попап не закрылся (ошибка валидации, сбой отправки) — вакансия всё равно помечается как успешно отправленная.
   - **Как поправить:** явно проверить результат ожидания закрытия попапа; если попап не закрылся за отведённое время — это ошибка/пропуск, а не успех.
   - **Как будет работать после правки:** «успешный отклик через попап» будет означать, что попап реально закрылся.

4. «Стоп» не останавливает уже начатую паузу перед кликом
   - **Важность:** стоит поправить
   - **Как сейчас работает:** статус прогона (`running`/`stopped`) проверяется один раз в начале обработки карточки, а дальше идёт скролл + случайная пауза 3–7 сек, и только потом клик.
   - **Что не так:** если пользователь жмёт «Стоп» именно в это окно паузы, клик по «Откликнуться» всё равно произойдёт — лишний, уже не желаемый отклик.
   - **Как поправить:** прямо перед самим кликом ещё раз перечитать статус из хранилища и, если он уже не `running`, прервать без клика.
   - **Как будет работать после правки:** «Стоп» гарантированно отменяет следующий клик, а не только следующую вакансию.

5. То же самое — на странице анкеты перед финальной отправкой
   - **Важность:** стоит поправить
   - **Как сейчас работает:** аналогично №4, но в `vacancy-questionnaire.js`: статус проверяется один раз в начале, а между этим моментом и кликом на «Отправить» проходит время на ожидание LLM-ответа и заполнение полей — статус повторно не проверяется.
   - **Что не так:** если «Стоп» нажат, пока идёт запрос к LLM или заполнение анкеты, отправка всё равно произойдёт.
   - **Как поправить:** перед кликом на «Отправить» тоже перечитать статус и прервать, если уже не `running`.
   - **Как будет работать после правки:** «Стоп» надёжно останавливает и анкетный сценарий, а не только сценарий списка.

- ✅ 2. Отправка анкеты считается успешной без подтверждения
- ✅ 3. Успех попапа с письмом тоже не подтверждается
